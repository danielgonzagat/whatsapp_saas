# WhatsApp Inbox — connect a real WhatsApp number, receive every customer message, reply (human or AI), all scoped per workspace

> **Territory root:** `backend/src/marketing/channels/whatsapp/`
> **Sibling territories it touches:** `backend/src/meta/` (the real inbound webhook + the Graph API send client), `backend/src/inbox/` (conversation/message read model + human reply), `backend/src/kloel/whatsapp-emitter/` (domain events).
>
> **Provider reality (read this first):** The ONLY live WhatsApp transport is the **Meta WhatsApp Cloud API**. **WAHA is intentionally deprecated** — the old WAHA QR/browser-session runtime was removed in the "Meta-only migration". Files and types still carry `Waha*` names (e.g. `WhatsAppApiProvider`, `WahaChatMessage`, `whatsapp-api.provider.ts`) — these are **legacy names for the Meta-backed implementation**, not a second live provider. The legacy WAHA webhook (`/webhooks/whatsapp-api`) still exists but only logs-and-ignores. Do not treat WAHA as a gap; treat it as a closed chapter.

---

## 1. Purpose

Give each workspace a working WhatsApp business line: connect a Meta-verified number, **receive** every inbound customer message exactly once (idempotent), persist it into a conversation, and **send** outbound replies — typed by a human in the inbox or generated by the Autopilot AI — back through Meta. Everything is isolated per `workspaceId`.

## 2. What the user does

1. Opens **WhatsApp** in the app and connects their number (Meta Embedded Signup / OAuth — owner grants the Meta business asset). The UI shows a connection card and live status (`QrConnectCard.tsx`, `WhatsAppConsole.tsx`, `useWhatsAppSession.ts`).
2. A customer messages the business number on WhatsApp. Meta delivers it to our webhook; it appears in the **Inbox** as a new/updated conversation.
3. The user reads the thread and either types a reply (sent out via Meta) or lets **Autopilot** answer automatically. They can pause/resume the AI per conversation.
4. The inbox reflects honest states: connected / setup-required / degraded (if Meta is unreachable) — never fake "sent".

## 3. End-to-end flow (real paths)

### A. INBOUND (customer → us) — the live path
```
WhatsApp customer
  → Meta Cloud delivers POST to our public webhook
  → backend/src/meta/webhooks/meta-webhook.controller.ts
        MetaWebhookController.handleWebhook   (route: POST /webhooks/meta, @Public)
        ├─ HMAC-SHA256 verify of x-hub-signature-256 vs META_APP_SECRET   (FAIL-CLOSED: no secret OR bad sig → 403)
        ├─ idempotency layer 1: redis.set(key,'1','EX',300,'NX')  → duplicate ⇒ return 200 'ok'
        ├─ idempotency layer 2: webhooksService.logWebhookEvent('meta',…) → WebhookEvent @@unique([provider,externalId]); P2002 ⇒ return 200
        └─ object 'whatsapp_business_account' → handleWhatsAppCloud → handleWhatsAppMessagesChange
              ├─ metaWhatsApp.resolveWorkspaceIdByPhoneNumberId(phone_number_id)   ← multi-tenant resolution
              ├─ metaWhatsApp.touchWebhookHeartbeat(ws,{status:'connected'})       ← liveness
              ├─ for each message: processIncomingWhatsAppMessage(...)
              │      → InboundProcessorService.process({ provider:'meta-cloud', ingestMode:'live', providerMessageId, from, text, raw, … })
              └─ for each status: updateWhatsAppStatus(...)  → prisma.message.updateMany(status,errorCode)  ← delivery/read receipts
  → backend/src/marketing/channels/whatsapp/inbound-processor.service.ts
        InboundProcessorService._processImpl  (the canonical inbound pipeline)
        ├─ idempotency layer 3: checkDuplicate(ws, providerMessageId)  (Redis dedupe key + Message.externalId lookup) ⇒ {deduped:true}
        ├─ guard: isWorkspaceSelfInbound → drop own-number echoes
        ├─ prisma.contact.upsert  (where workspaceId_phone)            → RAC_Contact
        ├─ inbox.saveMessageByPhone({direction:'INBOUND', externalId})  → RAC_Message (+ RAC_Conversation)
        │      └─ on P2002 (race): re-find existing → cache → {deduped:true}   ← idempotency layer 4 (DB unique)
        ├─ redis.set(dedupe key, savedMessage.id, 'EX', 300)
        ├─ decisionOutcome.recordEvent('inbound.received')
        ├─ whatsappEmitter.emitMessageReceived(...)                    → commerce.whatsapp.message_received
        ├─ deliverToFlowContext (flowQueue 'resume-flow') if not catchup
        ├─ voiceQueue 'transcribe-audio' if audio
        ├─ accountAgent.detectCatalogGap(...)
        ├─ triggerWhatsappMindPercept(...)                             → CIA/Mind cognition
        └─ triggerAutopilot(ws, contactId, phone, content, …)         → AI reply (autopilot territory)
```

### B. OUTBOUND (us → customer) — human or AI reply
```
Inbox UI reply  → frontend → POST /inbox/conversations/:id/reply
  → backend/src/inbox/inbox.controller.ts  InboxController.replyToConversation
  → backend/src/inbox/inbox.service.ts     InboxService.replyToConversation
        ├─ resolve conversation + contact.phone (scoped by workspaceId)
        ├─ channelTransports.send({channel:'whatsapp', recipientId:phone, content})
        └─ on success → saveMessage({direction:'OUTBOUND', status:'PENDING'})  → RAC_Message

(programmatic / autopilot send path)
  WhatsappService.sendMessage(ws,to,msg,opts)                         whatsapp.service.ts
   → WhatsappMessageDispatcherService.sendMessage                     whatsapp-message-dispatcher.service.ts
       ├─ WhatsappSendRateGuardService (anti-burst / dedupe)          whatsapp-send-rate-guard.service.ts
       ├─ planLimits.trackMessageSend(ws)                             → RAC_DailyMessageCounter (quota)
       ├─ WhatsAppProviderRegistry.sendMessage                        providers/provider-registry.ts
       │     → provider-send-message.helpers.ts → metaCloudProvider.sendMessage
       │       → WhatsAppApiProvider.sendMessage                      providers/whatsapp-api.provider.ts
       │         → MetaWhatsAppService.sendTextMessage / sendMediaMessage   meta/meta-whatsapp.service.ts
       │           → Graph API  POST {phoneNumberId}/messages          (the real wire call)
       └─ inbox.saveMessageByPhone({direction:'OUTBOUND', externalId: meta wamid})  → RAC_Message
  → Meta later POSTs a status webhook → updateWhatsAppStatus → Message.status (sent/delivered/read/failed)
```

  → Next proxy: frontend/src/app/api/whatsapp-api/**/route.ts  (proxyWhatsAppRequest → backend, attaches auth + workspace)
  → WhatsAppApiController (@Controller('whatsapp-api'))         controllers/whatsapp-api.controller.ts

  → WhatsAppMetaCompatController (session/link, claim, action, takeover, resume-agent, stream-token, …)

### D. CATCH-UP (history backfill)
`WhatsappCatchupOrchestratorService` (+ `WhatsAppCatchupService`, `WhatsappCatchupHistoryService`) replays older Meta chat history into the same `InboundProcessorService.process({ ingestMode:'catchup' })` pipeline — silent (no unread bump, no autopilot trigger), reusing all four idempotency layers.

## 7. Workspace isolation

- **Tenant resolution on inbound:** `MetaWhatsAppService.resolveWorkspaceIdByPhoneNumberId(phone_number_id)` maps the Meta number to exactly one `workspaceId` before anything persists. Unresolved → logged + dropped (no cross-tenant leak).
- **Every Prisma call is workspace-scoped:** `contact.upsert(where: workspaceId_phone)`, `message.findFirst(where:{workspaceId,externalId})`, `conversation.findFirst(where:{id,workspaceId})`, `message.updateMany(where:{workspaceId,externalId})`.
- **Authenticated routes** (`whatsapp-api`, `inbox`, `whatsapp/:workspaceId`) use `JwtAuthGuard` + `WorkspaceGuard`; the Next proxy injects the active workspace; controllers prefer `req.workspaceId` over any path param.
- **Idempotency keys are workspace-qualified** (`buildInboundDedupeKey(workspaceId, providerMessageId)`), so dedupe never collides across tenants.
- **Self-inbound guard** drops the workspace's own number echoes.

## 8. Honest status

**Works end-to-end (evidence in code + tests):**
- ✅ **Inbound idempotency is genuinely robust** — four independent layers: Redis `SET NX`, `WebhookEvent` unique constraint, processor `checkDuplicate`, and a `Message.externalId` P2002 race-catch. Covered by `webhooks/whatsapp-api-webhook.controller.spec.ts`, `inbound-processor.service.spec.ts`, and `whatsapp.service.*.spec.ts` (15+ part-spec files in this dir).
- ✅ **Webhook signature verification is fail-closed** — missing `META_APP_SECRET` or bad `x-hub-signature-256` → 403 (`meta-webhook.controller.ts:171-186`).
- ✅ **Outbound send reaches the real Graph API** via `MetaWhatsAppService.sendTextMessage` → `{phoneNumberId}/messages`, with rate guard + plan-limit quota + outbound persistence + status-receipt reconciliation.
- ✅ **Per-workspace tenant resolution** by phone_number_id is real and enforced before persistence.
- ✅ **Honest degraded states** — `WhatsAppMetaCompatController` returns `notSupported:true` (not fake success) for WAHA-only endpoints; session/connection surfaces `degradedReason`/`meta_connection_required`.
- ✅ **Catch-up history backfill** reuses the same idempotent pipeline with `ingestMode:'catchup'`.

**Facade / depends on owner-gated config / unproven at runtime:**
- ⚠️ **Live connection requires owner action**: a workspace only works once the Meta number/token are provisioned (`MetaConnection`) and `META_APP_SECRET` / `META_VERIFY_TOKEN` are set in Railway. Without them the webhook is fail-closed (correct, but means "connected" is owner-gated, not self-serve-complete).
- ⚠️ **Runtime not independently verified in this pass** — correctness is asserted from code + unit specs, not from a live Railway message round-trip here. PULSE `pulse_health_by_module` returned no module-scoped artifacts (needs `pulse_scan` first), so no module health % is cited.
- ⚠️ **Legacy WAHA naming debt** — `Waha*` types and `whatsapp-api.provider*` filenames describe the Meta implementation; cosmetically confusing but functionally correct. Not a runtime gap.
- ⚠️ The legacy `WhatsappController` (`/whatsapp/:workspaceId/*`) and `WhatsAppApiWebhookController` (`/webhooks/whatsapp-api`) are compatibility shells; the latter only logs-and-ignores. Safe to keep, candidates for eventual removal.
